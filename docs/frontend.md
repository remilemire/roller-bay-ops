# Frontend workspace

The Next.js App Router app in `apps/web` provides the operational workspace. It uses the existing Nest API and shared Zod contracts; it does not store business records in Next.js or connect directly to the database.

## Organization

| Directory under `apps/web/src` | Responsibility                                                                                                        |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `app/`                         | Thin route entries, layouts, providers, loading and error boundaries.                                                 |
| `features/`                    | Domain screens, API operations, query keys, form conversion, and tests.                                               |
| `components/ui/`               | Locally owned shadcn-style primitives using Radix, CVA, and Tailwind, adapted to the workspace theme.                 |
| `components/layout/`           | Dashboard shell, navigation, account menu, and theme control.                                                         |
| `components/records/`          | Record value rendering shared by history, correction reviews and submitted cutting results.                           |
| `components/corrections/`      | Correction review-and-submit flow and blocker lists shared by the stock, receipt and completion correction editors.   |
| `lib/`                         | Credentialed HTTP client, error descriptions, query defaults, formatting, measurement conversion, and pending keys.   |
| `styles/`                      | Semantic light/dark tokens in `theme.css`; shared layout, components, responsive styles, and motion in `globals.css`. |

The `(auth)` and `(dashboard)` route groups select layouts without changing URLs. Layouts remain server components; authenticated workflows mount inside a client authentication boundary. Shared components accept data and callbacks without importing domain features. Features can consume another feature's exported API queries or lookup functions, but not its screens or editors: when a screen shows another feature's UI, such as an order's production log or history, it takes that section as a slot prop and its route composes the two. Routes that pass callbacks or components are client pages; a route without a dynamic segment that reads `searchParams` stays a server page, since a client page there is prerendered with empty parameters.

`components.json` configures the local shadcn component directory and aliases. Shared public schemas remain in `packages/shared`; UI components remain in the web app. See [shadcn's Next.js setup](https://ui.shadcn.com/docs/installation/next).

## Implemented workflows

| Route                                                                                    | Behavior                                                                                                                                                                                                                                                                                                                                    |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/login`                                                                                 | Microsoft sign-in and authentication errors.                                                                                                                                                                                                                                                                                                |
| `/`                                                                                      | The two order queues (to allocate, to schedule), stock and allocation counts, shared draft counts, the orders shipping this working week, recent arrivals, and workflow links, all from existing list APIs.                                                                                                                                 |
| `/fabric-catalog`                                                                        | Manufacturer → material → color tree; search across all three and admin create/edit/delete dialogs.                                                                                                                                                                                                                                         |
| `/locations`                                                                             | Levels, sections, and zones; searchable lists and admin create/edit/delete dialogs.                                                                                                                                                                                                                                                         |
| `/stock-items`, `/stock-items/:id`                                                       | Stock search, lifecycle filters, detail, source links, and admin opening-stock/correction forms.                                                                                                                                                                                                                                            |
| `/stock-receipts`, `/stock-receipts/new`, `/stock-receipts/:id`                          | Shared draft entry, revision-aware saves/deletion, confirmation, and resulting stock links.                                                                                                                                                                                                                                                 |
| `/work-orders`, `/work-orders/:id`                                                       | Production orders as a Monday–Friday week board, a list, or a month calendar, with history; the board opens first, and the list has a status filter that opens on unshipped orders and order-number search; admin add, schedule, reschedule and mark shipped from the row or the order's page, note editing and delete on the order's page. |
| `/allocations`, `/allocations/new`, `/allocations/:id`, `/allocations/:id/cutting-sheet` | Requirements, cutting rules, manual cuts/assignments, generated/validated plan previews, shared drafts, confirmation, active-plan replacement, cancellation, a printable cutting sheet, and cutting-result entry; the list opens on active allocations.                                                                                     |
| `/users`                                                                                 | Admin/owner user directory: search by name or email, role changes, deactivation and reactivation, and owner-only ownership transfer, each behind a confirmation dialog.                                                                                                                                                                     |
| `/settings`                                                                              | Current account, per-field measurement units, and appearance preference.                                                                                                                                                                                                                                                                    |

Admins and the owner can modify catalog, locations, stock records, and work orders. Staff accounts can manage receipt and allocation workflows; production accounts are limited to their assigned stations, and pending accounts see an approval notice. The backend authorizes every request. The Users link and directory are shown only to admins and the owner; other roles see no directory data. The directory offers no actions on the owner or on the signed-in user's own row, so ownership changes only through a transfer and nobody locks themselves out from this screen. A transfer refreshes the session so the previous owner's role updates immediately. Dashboard figures use existing paginated totals.

Work orders have three views, chosen by the `view` URL parameter: the week board (default, so it needs no parameter), `month`, and `list`. The week board shows Monday to Friday of the week containing `week` (any day; the current week by default, or the coming one on a weekend) with totals by status for the week above the board. Each day is a panel with a heading band, its orders as rows of one divided list, and a footer band for the day's totals, currently its order count. An empty day says "No orders". Above the days a To schedule tray holds the allocated or back-ordered orders that have no ship date yet (the API's `unscheduled` queue, at most 100, with a link to the list for the rest), outside the week's totals. Admins drag an order from the tray onto a day to schedule it, to another day to reschedule it, or back onto the tray to clear its date, by pointer on the whole card or by keyboard from its handle (Space, Left/Right a stop at a time with the tray before Monday, Space; Escape cancels), with each step announced. The board has a search box for finding an order without scanning for it, kept in the `search` URL parameter that the list shares. The tray, which can hold a hundred orders, is narrowed by the API; the days keep every order, so their totals still mean the day, with the matches marked and the rest dimmed. A line under the box counts the matches on the page and links the ones that are not on it: an order shipping in another week to that week, an order with no allocation to the entry screen, and past five of them to the list. A pointer drop lands on the day under the pointer, because a tray card is wider than a day and its centre can sit over a neighbour; the keyboard uses the nearest centre. A drop shows at once, is saved with the order's revision, and is put back if the save is refused; one move saves at a time. The month calendar shows `month` (`YYYY-MM`) as a Monday-to-Friday grid including the edge weeks' neighbouring days, lists up to four orders a day coloured by status, and links the rest to that day's week. A Today button between the previous and next arrows returns to the current week or month, as in most calendars. Both calendar views show only orders that have a ship date, in every status, and are read-only for employees. An order is not added to a day: the page's New order button opens the Add order dialog, which takes the six-digit number, the blind count and, for admins, a note and an optional back order (its purchase-order numbers and a ship date), and creates the order alone. The dialog closes and the page stays where it was; the new order waits in the list's To allocate tab, and reaches a day on its back order or by being scheduled once fabric is allocated for it. A number that is taken says so and links to that order, as on the entry screen below. They read every page of the API's ship-date range, since a page holds at most 100 orders. Dates elsewhere are picked with `DateField`, a month grid that opens in the document flow with arrow-key, Home/End, and PageUp/PageDown navigation; ship dates use its weekday-only grid. The views compute days with `lib/calendar-dates`, which treats every day as UTC midnight.

The list keeps its status filter, search, and page in the URL; with no `status` parameter it lists open orders, and `status=all` includes shipped ones. Two of its tabs are work queues: To allocate (`status=new`, orders with no allocation) and To schedule (`status=unscheduled`, allocated or back-ordered orders with no date). Ship dates are calendar days: the form sends the date input's `YYYY-MM-DD` string unchanged and `calendarDateLabel` formats it in UTC, so a Friday never displays as Thursday west of Greenwich. An order's blind count is stated when it is added. The list, the week cards, and the month days show the counts; the week shows each day's orders and blinds in its footer and the week's above the board. Admins edit an order's blind count and note with its page's Edit action; the count is read-only while the order has an allocation. The dialog is pinned to the order and revision it opened with, leaves out an unchanged count, and shows an API issue on either field beside it. Every open order's row and page have a Schedule action for admins, Reschedule once it has a date, with the revision it opened with; clearing the date takes the order off the schedule. For an allocated order the dialog opens with the weekday-only calendar showing and saves only the date. For an order without an allocation it also takes the back order, its purchase-order numbers typed into one box and separated by commas or spaces, which the API requires before a date; the API's issues show beside the field they name. Such orders also have an Allocate action, open to employees too, which opens the entry screen on that order. An order waiting on a back order shows its purchase orders on its row, card and page in place of the missing-fabric flag, and its page keeps them once fabric is allocated. Each row's ship toggle sends the revision the row shows and needs no confirmation because it is reversible; the list refreshes whether or not the request succeeds, so a refused stale row comes back current. An order's page links to its allocation through the allocation search in every state, since the allocation may already be completed or cancelled, and allocation confirmation, replacement, cancellation, and completion invalidate the schedule queries because they move an order's status. In the allocation editor a 409 that carries a field issue, such as an order that is already allocated, shows with the field it names, or above the form when it names the order, and does not offer to reload the draft.

A new allocation starts at `/allocations/new`, reached from the New allocation buttons on the dashboard and the allocations list. Its Order panel picks the order with a search box over the `unallocated` work orders, the open ones with no live allocation, each labelled with its number and blind count; an order that needs fabric again after its allocation was cancelled is among them. The panel's Add order button opens the same add-order modal as the schedule, composed by the route as a slot because the form belongs to work orders; the order it creates is picked at once. Searching the picker for a full six-digit number that no listed order has offers "Create order" and that number as a last option, which opens the modal with the number filled in. A number that is taken says so in the modal and links to that order, to be allocated if it still needs fabric or opened if not; the 409 names no order, so the form reads it by its number. `?workOrder=<id>` opens the editor with that order picked, as the Allocate actions do; the page keys the editor by the id because the form reads it once. Save draft and Confirm allocation wait for an order. A draft may be moved to another order with the picker, taking its blinds along; an active plan stays with its order, which it shows without a picker, and an API issue about its order shows above the form. The order asked for comes before a pending earlier request, which saving then refuses to pass until it is restored and retried.

## Authentication and API requests

`NEXT_PUBLIC_API_URL` is the public API base URL, including `/api`, and is embedded at build time. It defaults to `http://localhost:3001/api`. The browser navigates to `/auth/login`; OAuth, domain restrictions, HttpOnly cookies, and Redis sessions stay in the backend. `/auth/me` supplies the current user. The web app never reads access tokens or session cookies.

Every API call uses `credentials: 'include'`. Mutation requests send JSON and, where required, `Idempotency-Key`. Response schemas validate successful API data. A 401 from a protected request ends the client session and clears private queries, mutation results, and pending submission payloads. The session query handles its own signed-out response without cancelling itself. A deactivated account receives an access error. An ordinary 403 on a feature operation remains a permission error. Error bodies are parsed with the shared [error envelope](errors.md); `ApiError` carries `status`, `message`, optional `retryAfterMs`, and `issues`. `ErrorNotice` shows the API's curated message and lists field issues with readable labels; text from any other exception is replaced by generic copy. `TextField`, `ChoiceField`, and `Lookup` take an `error` that renders beside the control and marks it invalid. Each form maps issue paths onto its own fields (for example `allocationFieldName`, which also covers plan-validator paths, and `receiptFieldName`), places them with `lib/field-issues`, and passes `ErrorNotice` the same mapping as an `inline` filter, so the notice lists only issues without a field of their own; an inline error clears when its field is edited. Correction forms receive their messages from `CorrectionSubmit`, which maps indexes in the filtered request lists back to the edited line or stock item; those messages describe the last review or save and stay until the next one.

TanStack Query owns server data. Queries stay fresh for 30 seconds by default; session data uses 15 seconds and refreshes on window focus. Network, 429, and server failures receive at most two query retries with backoff; `Retry-After` is respected when supplied. Mutations never retry automatically. Successful writes invalidate affected feature queries. There are no optimistic stock, reservation, or submission updates.

Configure the backend's `WEB_ORIGIN` to the actual browser origin. Normal development uses `http://localhost:3000`; browser tests build the app and serve that production build on port 3100 with intercepted API responses ([testing](testing.md#browser-tests)). If testing manually on another port, update local backend configuration accordingly. Production requires the same-site HTTPS setup described in [authentication](authentication.md).

## Forms, measurements, and drafts

Search, filters, tabs, and pagination live in URL parameters. React Hook Form owns unsaved input. Form strings convert to shared Zod request schemas near the feature boundary; unfinished dimensions, quantities, and selections remain null. Drafts use the existing typed draft APIs and keep their IDs on submission.

- Each signed-in user chooses a unit per measurement field in Settings: inches, feet, yards, millimetres, centimetres, or metres. The fields are roll width, roll length, blind width, finished drop, drop allowance, cut length, edge trim, minimum reusable width and length, fabric thickness, radial depth, and tube outer diameter. The choice is stored on the user record (`measurementUnits` on `/auth/me`, changed through `PATCH /users/me/measurement-units`) and applies to inputs and displays everywhere.
- Defaults are **inches** for widths, drops, allowances, trimming, and minimum reusable sizes, **yards** for roll length, and **millimetres** for thickness, radial depth, and tube outer diameter. Settings groups the fields into stock dimensions, blind dimensions, cutting and remnants, and roll measurements, and can reset every field to its default.
- Operational timestamps are displayed in the facility's IANA time zone, configured at frontend build time with `FACILITY_TIME_ZONE` (default `America/Edmonton`). Production correction inputs are interpreted in that zone; nonexistent local times during a daylight-saving transition are rejected. Ship dates remain calendar dates without a time zone.
- Finished drop, drop allowance, cut length, edge trim, tube outer diameter, and radial depth carry an info tooltip wherever they are entered or shown, including Settings. The texts live in `measurementHelp` (`lib/measurements.ts`) and omit configured amounts, which come from API settings. Fields with help label their control explicitly and describe it with the tooltip text.
- All API dimensions remain millimetres with the existing precision constraints. Editable values in any unit preserve a round trip to 0.001 mm; display values may be abbreviated. An open editor keeps the units it started with, so a background session refresh cannot relabel or reinterpret unsaved input.
- Stock creation/corrections distinguish unused rolls, measured used rolls, and remnants. Explicit remaining length is reserved for remnants.
- Reference fields (fabric colors, locations, stock items, catalog and location parents) are search-as-you-type boxes. Focusing one opens the list under it with the first 25 matches for the typed text; while the list is open the box holds only the search text and shows the current selection as a faded placeholder, and closed it shows the selection's label. Arrow keys or Tab move through the options (Tab past the last one leaves the field), Enter or a click picks one, and Escape closes the list before it would close a surrounding dialog. Backspace on an empty search or on the shown selection, or the clear button, removes the selection. The list renders in the page flow rather than floating, so it works inside panels and dialogs alike.
- List search boxes search as the user types, 300 ms after the last keystroke, and at once on Enter or when the box loses focus. The box keeps its own text while focused, so a screen that trims the search does not move the caret; a search changed elsewhere, such as by a link, replaces the text. The paged lists keep their previous rows on screen while the next results load.

Saving a draft is explicit. An editor retains the record and revision it opened with, even if background queries see a newer revision or a confirmed record. A temporary background failure displays an error without unmounting the draft. Conflicts preserve input; reloading saved draft contents requires an explicit discard confirmation. Active-plan edits and cutting results likewise retain their original allocation/stock revisions. Confirmation requires a complete draft, and the backend revalidates current stock atomically. The submit endpoints act on the stored draft, so confirming an allocation or submitting a receipt with unsaved input first saves it to the same draft as an ordinary revision, then submits that revision. The receipt purchase-order-number field accepts digits only and warns once left unless blank or the full five digits; a receipt draft may still be saved with a partly entered number, and submission requires all of them. The allocation editor edits one record: the allocation's blinds and the plan that cuts them, saved together as a draft, or by Update reservations for an active plan. A blind's fields may be left blank in a draft and are sent as null; confirmation requires them. A draft's blinds may differ from the order's blind count. Confirm allocation, or Update reservations on an active plan, checks the count first: while it differs, it says what the order has and what the blinds add up to, and goes no further; the message stays, updating, until they match. The API makes the same check. Generating and validating plan the blinds in the form, so they need no save first. Removing a blind removes its assignments from the plan. The form is dirty against the draft or plan it opened with, and a background refetch never replaces it.

New draft creation and cutting completion keep their request key and exact payload in user/workflow-scoped session storage until success. Retrying an uncertain response uses the same key and payload; changed input cannot silently become a duplicate request. The editor can restore the earlier pending payload. This is submission retry support, not autosave or offline editing. Receipt/allocation draft submission retries use the saved revision as defined by their API.

Unsaved long forms warn before document unload and ordinary in-app link navigation. Browser history navigation is not intercepted; save a draft before leaving. Background refetches do not replace dirty values. Completion forms are not drafts, and active allocations cannot be reopened as drafts.

The allocations list keeps its state tab, search, and page in the URL; with no `state` parameter it lists active allocations, and `state=all` adds drafts, completed and cancelled ones. A cutting plan starts in one of two ways: **Generate plan** asks the backend optimizer for cuts, and **Add cut** builds the plan by hand. Generating over an existing plan asks before replacing its cuts. A generated plan is a preview until confirmation and makes no global-optimality claim; it can be edited and validated before saving, and a running generation can be cancelled. Feedback from generating or validating appears in one place between the plan and the form actions, both while the request runs and once it returns. Completion records consumed stock, measured returned rolls, returned remnants, and retained scraps, then shows any affected allocations flagged for replanning.

## Theme and responsiveness

[next-themes](https://github.com/pacocoursey/next-themes) applies light, dark, or system appearance before paint and stores the preference locally. Theme-dependent controls wait for hydration. The Appearance card in Settings offers five color palettes: Sage, Slate (the default), Ocean, Sand, and Plum. Each preview card uses the actual palette tokens and follows the current light/dark mode. Palette selection is independent of light/dark/system mode. The palette is stored on the user record (`colorTheme` on `/auth/me`, changed through `PATCH /users/me/color-theme`) and follows the account across browsers; the mode stays in local storage under `roller-bay-theme`. The picker and the applied palette both follow the session's value, so a change applies when the server responds and a failed save stays on the saved palette; other tabs pick it up on their next session refetch. `roller-bay-color-theme` in local storage only caches the last applied palette so a head script can paint it before the session loads, including on the sign-in page; invalid, missing, or blocked values fall back to Slate until the session arrives. Palettes chosen in a browser before the move to the account are not migrated. Semantic surface, foreground, border, accent, shadow, and glass tokens are shared across features.

Color, surface, border, and shadow transitions use a short coordinated duration. Reduced-motion preferences disable them; layout is not animated. Glass surfaces fall back to solid surfaces when backdrop filtering is unavailable. The desktop sidebar becomes a touch-accessible navigation dialog on tablet and smaller displays. Forms reflow and tables can scroll horizontally without forcing the page wider. Dialogs use Radix focus handling and Escape dismissal.

Shared spacing lives in `globals.css`: `.stack` separates sections by 24px and owns the gap instead of adding child margins; forms use a 16px field gap. Panel headings, bodies, table cells, and footers share the panel inset (24px, 18px on small screens). Completion records and expandable history rows use the same 24px line height and 10px vertical padding, with a 44px minimum row height. Keep compact calendar/tree layouts distinct from these record lists.

### Shared control and layout conventions

- Standard buttons, text inputs, selects, lookup inputs and date triggers use a 44px control height and a 10px radius. Compact buttons and segmented filters use 36px on desktop and 44px at the tablet breakpoint. Station measurement inputs deliberately keep their 48px height; checkbox sizing is separate.
- `SegmentedControl` provides exclusive filters and view selectors with a named group and `aria-pressed` selection. Its screen owns the URL state and default. Work-order views appear as Week, Month, List, with Week selected by default. Stock opens on On hand, receipts on Submitted, allocations on Active, and the order list on Open.
- Section stacks use 24px gaps, single-column `form-stack` and two-column `form-grid` use 16px field gaps, and action groups use 8px gaps. Actions wrap when needed. Put cancellation/secondary actions before the primary submission; use `form-actions` for the right-aligned form footer. Error notices belong above or below an action group, never between its buttons.
- Use `form-fieldset` for disabled groups without native fieldset decoration. Its zero minimum width lets fields shrink within a panel. Keep existing panel padding when a fieldset is itself a panel body.
- Load failures use `ErrorNotice` with a retry callback. Its retry button never submits an enclosing form. Lookup failures use a described inline error and the shared outline retry button; field validation uses the danger token and describes the relevant control. Only filter an issue from the summary when the corresponding field is actually rendered.
- Plan-validation details use the same readable issue labels and list spacing as API errors. Expected local selection failures belong beside the picker; arbitrary exception messages remain hidden behind generic error copy.

See the [frontend consistency audit](frontend-consistency-audit.md) for coverage and retained differences.

## Verification

From the repository root, build shared contracts before running the web workspace alone:

```sh
npm run build --workspace=@roller-bay/shared
npm run typecheck --workspace=@roller-bay/web
npm run lint --workspace=@roller-bay/web
npm run test --workspace=@roller-bay/web
npm run build --workspace=@roller-bay/web
npx playwright install chromium
npm run test:e2e --workspace=@roller-bay/web
```

Vitest and React Testing Library cover API errors, error envelope parsing, issue labelling, the error notice, cache clearing, query retries, the lookup box, unit conversions and per-field unit preferences, nullable drafts, assignment validation, submission-key reuse, retained completion results, and preservation of dirty forms/revisions during background updates. Playwright covers desktop and tablet navigation, theme persistence/transitions/reduced motion, session expiry/logout/deactivation, permissions, catalog editing, receipt conflicts and submission retries, allocation plan generation/draft confirmation, and completion measurements.

Browser tests intercept API requests using fixtures shaped by the real shared contracts. They verify the browser's behavior and outgoing requests without changing a database. They do not replace the backend's PostgreSQL/Redis/solver integration suites or live Microsoft tenant testing. Trace files, screenshots, and browser reports are ignored by Git.

Allocation forms collect finished blind sizes and quantities. Edge trimming, reusable-remnant thresholds, and extra drop allowance are server configuration, not editable form fields. Saved allocation details still display their recorded rules and allowances in the user’s preferred units.

## Corrections and history

Stock, submitted receipts and completed allocations expose admin correction actions and employee-readable history. Forms pin their opening revisions and units, require a reason and review, preserve input on conflicts, and retain the exact payload/key for uncertain retries. Receipt and completion contexts explain blocked records and link to related orders. Voided stock has a separate list filter; corrected printed allocation details identify their correction date. See [corrections and audit](corrections-and-audit.md) for operational rules and schema rollout.
